## 第一部分 评价

### 1.1 总体判断

这是同类个人／小团队 FPGA 项目里少见的"可执行规格书"，不是构想稿。它的真正价值不在故事，而在**防止自欺的记账纪律**——这一点比多数商业项目严格。

但它在两个地方有硬风险：时序，以及 BRAM 账的条件依赖。

| 维度 | 判断 |
| --- | --- |
| 工程严谨性 | A− |
| 游戏／叙事设计 | B |
| 风险控制 | B− |
| 文档可执行性 | B（论证充分，但过长，缺少一页门禁清单） |

### 1.2 做得确实好的地方

1. **基线固定得干净。** 11,815 LUT / 4,447 FF / 15.5 BRAM / WNS +0.076，每个数字都带报告路径，并且明确"不能拿音频加入前的 11,525 当现状"。这类源码与 bit 错配是同类项目最常见的翻车点，文档提前堵住了。
2. **反自欺条款很硬。** "不能同时宣称保留原 ROM 又扣除它""模块级综合数不能直接减全工程布线数""不得放宽像素时钟、添加虚假 false path 换通过""只有代码更统一而未达到画面／功能／资源目标不算验收"。这几条是真踩过坑的人写出来的。
3. **唯数据源思路贯穿到底。** `build_story_assets.py` 从单一颜色／字形／文本描述生成三处表（画面 RTL、`net_screen_tx.v`、PC 端 `DEFAULT_PAL`），直接消灭本项目"三份调色板各改各的"的真实故障模式。这是全篇最有价值的单个设计决定。
4. **8 段／4 阶段／2 段一档的映射很漂亮。** 阈值 `2,4,8,12,18,24,28,32` 正好每阶段 2 段，且与参考图"5/8 亮 + 一个琥珀充能边界"完全对得上（即 STABILIZE 中段）。这种自洽度说明数字是算过的，不是拍的。
5. **第 1 轮实测验证了预算模型。** 预估 +50～180 LUT，实际 +107（11,922）；337 项任务专项检查、29,769 项元数据比对、14 套完整回归。粗估第一次就命中区间，说明 §12 的估算方法有校准。

### 1.3 主要问题（按严重度排序）

#### P0 — 时序没有对应方案，而余量已经在滑

基线 WNS +0.076 ns，第 1 轮已降到 **+0.023 ns**，低于文档自己定的 +0.050 目标，记录里只写了"下一轮简化画面路径继续改善"。

而后续三轮恰恰要往最热的像素路径上加东西：24 格距的 `floor(u/3)` 查表、文字双口 ROM 的两次同步读 + 前取、图块 ROM 同步读、ADPCM 解码与三路混音。74.25 MHz 像素时钟不变。

文档只有一串禁令，**没有一条收敛手段**（例如：文字平面单独延一拍再与延后的 `psel` 合成；把 `psel/psel_r` 链切开；所有图层输出先打寄存器再进合成）。这是唯一能让整个计划停摆的风险，却是全篇技术密度最低的一节。

#### P0/P1 — 配音的 16 tile 是硬支出，字库的 −7 tile 是条件收入

`15.5 + 16（语音）+ 0.5（图块）− 7（字库）= 25`，占 50%，账算得对。但若字库只回收一半（−3.5），就是 28.5，**超过文档自己定的 28 tile 上限**。

也就是说：语音 ROM 的可行性在数学上依赖字库回收全部成功。而字库回收排第 2 轮、语音排第 5 轮。应改为硬门禁：**字库回收通过网表验收，才允许冻结语音 ROM 容量。**

#### P1 — 24 像素格距是自找的组合开销

为了留画面空间，把 `(hcounter-321)>>5` 换成 `>>3` + 小表 `floor(u/3)` + 乘法式减法，文档自己都承认"两个异步读口会有复制成本"——全都压在像素最热路径上。

而 16 格距（纯移位，场地 384×320，留白更多、栅格工作量更小）与 32 格距（零改动）都更便宜。文档把 24 px 写成默认、把 32 px 写成"失败后的回退"，顺序反了。**24 px 应先自证收益再采纳**，而不是先建 `story_layout.vh`。

#### P1 — 语音预算与台词粒度不匹配

8 句 / 16 秒 = 平均 2 秒一句。但 V0 是两句 `CORE LINK ESTABLISHED.` + `BEGIN REPAIR.`，正常语速就要 3 秒以上。

文档一边写"不能为了凑秒数把语速压到听不清"，一边用一个必然压语速的预算。真实可选项只有三个：减到 5–6 句、把上限提到 20–22 秒（+2～3 tile）、或合并成单句。现在的数字是三者都不选。

#### P2 — "故事感"实际交付的是"情境感"

四段本质是可以看的进度条机器化：玩家能懂"我在修核心"，但没有人物、没有事故前因、没有代价，失败也只是一句 `REPAIR LINK LOST.`。

对 FPGA 约束这是**正确**取舍，但文档不该让 §16 读起来像做出了叙事。建议在结论节直说：本方案买到的是氛围 + 因果反馈 + 可读的阶段状态，不是故事。

#### P2 — 目标可读性押在最弱资产上

§16 第 1 条要求"不读说明就懂自己在修飞船核心"，但实现路径主要是 2 秒合成语音 + 阶段标题，而语音要到第 5 轮才做垂直验证。前 4 轮的画面里没有兜底说明。

建议第 2 轮就放一条静态两行目标文本。

#### P2 — 预算区间宽到不可证伪

+440～+1,880 是 4.3 倍跨度，这种区间不构成控制，只构成许可；真正起作用的只有 2,200 LUT / 28 BRAM 两条硬线。

而且"超限先削减什么"没有排序——§12 只写"先减少装饰、警示变化和额外声部"，与 §1 的优先级链没有对应。缺一条明确的削减顺序（建议：装饰 → 行星图块 → 语音句数 → 阶段背景变化）。

#### P3 — 三个小漏洞

- 计分不参与任何机制，是纯装饰，却仍列在 §9.1 的常驻信息里。
- ADPCM 每样本 `step × 4 bit 差分` 至少一次小乘法，"DSP 默认仍为 0"没有给出实现路径（时分复用？移位近似？）。
- NEXT=1、22 px 面、210 ms 档、锁存延迟／出生延迟／DAS-ARR **完全没进入计划**，而它们比画面更决定"能不能玩下去"。

### 1.4 几处文档漂移

- 基线提交号不一致：正文 §2.1 写 `616113c`，逐轮记录写 `68aa688`，正文未说明后者。
- "不再保留两份正文"没做到：v4～v9 五份历史文档仍在 `FPGA学习` 目录，重定向是三跳（v9 记录 → 资源版桩 → D: 正文）。
- v9 记录里的链接写成 `</C:/Users/...>` 这种非标准绝对路径形式。
- 49 KB 里相当篇幅是防御性论述（"不能…""不得…""不以…"）。它的价值是留证，但执行时更需要一页门禁清单。建议拆成"规格 + 决策理由"两册。

## 第二部分 建议：怎么改

### 2.1 一句话诊断

现在的东西是「状态机 + 状态报告」：玩家能看出**进度**，看不出**处境**。

缺的不是更多画面，而是两样——**一个会说话的对象**，和**一处看得见的伤**。这两样都不怎么吃资源，反而能替现有计划省钱。

### 2.2 三条原则

1. **文字负责状态，语音负责人物。** 现在 V0–V7 里 `BYPASS RESTORED` 这类是 UI 文案，却占着最贵的语音预算。状态改用屏幕文字（几乎免费），语音只留给情绪。
2. **一个持续可见的对象，胜过五处弥散的背景变化。** 玩家不会记住"第三盏维护灯变常亮了"，但会记住"那道裂缝合上了"。
3. **不破第 1 轮。** 所有改动只往第 2–6 轮加，第 1 轮的任务闭环、`accept_gameplay`、`story_controller` 全部复用。

### 2.3 改法 A：让 CORE-07 本身是说话的人（核心改动）

计划里 `CORE-07` 一直只是设备编号。把它改成**说话者**——你在修的那个东西在跟你说话。然后让**它的语音清晰度跟着修复进度走**：电力越足，话越完整。

这一下同时解决三件事：故事有了角色；8 kHz 窄带语音从"妥协"变成"美学"；16 秒预算从"塞不下"变成"绰绰有余"。

| 触发 | 台词 | 时长 | 用意 |
| --- | --- | ---: | --- |
| 开局 | `—…you came.` | 1.3 s | 断句、杂音、只有三个词。玩家第一反应是"它在跟我说话？" |
| 进 REBUILD | `Bypass… restored. I can see you.` | 1.9 s | 出现停顿和"看见"，比上一句流利一档 |
| 进 STABILIZE | `Containment holding. Keep feeding me.` | 2.0 s | 完整句子，开始有请求 |
| 进 RECHARGE | `Final charge. Hold it steady.` | 1.6 s | 语气变成指令，与玩家平等 |
| 危险（只留一条） | `Pressure rising. Clear the array.` | 1.8 s | 危急时语速最快、最清楚 |
| 成功 | `Power restored. …Thank you.` | 2.2 s | 全篇唯一一次完整、放慢、带停顿的句子 |
| 失败 | `No— not yet. Not—` → `[SIGNAL LOST]` | 1.9 s | **在样本中途截断**，字幕转成 `[SIGNAL LOST]` |

最后一句是全篇的支付点：整局都在听它恢复语言能力，失败时又被打断。**这条弧线不需要一行额外代码**——只是换台词、换播放长度。

预算：7 句约 12 s ≈ 12 tile，比原计划 16 tile **省 4 tile**；压到 10 s 则省 6 tile。

另把 V4/V5 两条危险合并成一条，危险只保留"新进入"一次，其余交给屏幕文字和警报音。8 句降到 7 句，正好腾出余量。

### 2.4 改法 B：一处会愈合的伤口

删掉 §7.1 里 5 处弥散背景变化中的 2–3 处（维护灯、外侧接缝、横向供能轨），换成**一个固定位置的中央对象**：船壳裂口，约 40×24 px，放在左上船壳面。

四张掩码，形状不变只改缺口：

| 阶段 | 裂口外观 |
| --- | --- |
| RECONNECT | 贯穿开口，边缘锯齿，内部纯黑 |
| REBUILD | 下半被一块补板盖住，仍有缝 |
| STABILIZE | 只剩一条细缝，两侧压条到位 |
| RECHARGE | 闭合，接缝为暗线 |
| 成功 | 接缝亮起一道焊光，保持 |
| 失败 | **缝重新裂开**（两帧反向），作为失败的反打 |

成本：约 40～60 LUT、0 BRAM，且能抵掉被删的几处背景逻辑。收益远大于成本——这是玩家唯一会主动回头看的东西。

### 2.5 改法 C：结尾 1.2 秒的收束

现在成功是「冻结 + 结算页等待操作」，情感上是断的。在结算页之前插 1.2 秒，无文字、无字幕、无人声：

1. 核心八段同时提亮两档（复用现有 mask）
2. 裂口焊光划过一次
3. **手套退出画面**——两帧固定偏移即可，用已预算的那块 64×32 精灵 ROM，不加新资产
4. 行星／船壳轻微提亮一次（`+1` 配色索引，不是新色）

这就是"角色对世界做了最后一个动作"。成本约 20～40 LUT、0 BRAM，比任何台词都有效。

### 2.6 改法 D：一条颜色语法

现在 56 色只是"够用"，没有语义。定三条规则，全屏立刻像是被设计过的：

- **青 / cyan** = 玩家的太空服与 AR（幽灵框、手套、系绳、字幕框边）
- **琥珀 / amber** = 核心能量与警戒（充能边界、危险括号、维护灯）
- **白 / white** = 已锁定、已完成（已落块高光、修好的接口、成功的焊光）

顺手把**幽灵改成青色虚线**：一下就解释了"玩家凭什么看得见落点"——那是头盔 AR 投影。同时把幽灵与智能提示天然分开（后者是白框）。

成本：0。全在 56 槽内重分配。

### 2.7 改法 E：开局 1.5 秒静场

现在 `new_run` 之后方块立刻开始掉，玩家从没机会"看"这个场景。加 1.5 s 预滚：空场地、核心明显是坏的、手套在画面里、V0 播完，再放第一个方块。

实现上几乎免费——第 1 轮已建好的 `accept_gameplay` 门控直接拿来用，只是让它多保持 1.5 s。

### 2.8 改法 F：两个小修

- **字幕停留 0.4 秒再收。** §10.4 写"播完立即收起"，会让人来不及读。加一个短计时器即可。
- **一条贯穿全程的底噪。** 不是四段四种氛围曲，而是**同一个低频嗡鸣**从开局存在、阶段切换时抖一下、成功时变稳。它把四个阶段缝成"一个连续处境"，而不是四个主题。复用已有振荡器，0 额外成本。

### 2.9 相对现计划的资源账

| 项 | LUT | BRAM |
| --- | ---: | ---: |
| 语音 8 句 → 7 句短句 | 0 | **−4** |
| 裂口替换 2–3 处背景变化 | +20 ~ 0 | 0 |
| 结尾 1.2 s 收束 | +20 ~ 40 | 0 |
| 开局静场 | +10 | 0 |
| 颜色语法／幽灵虚线 | 0 | 0 |
| 字幕停留 | +8 | 0 |
| **合计** | **+60 ~ +80** | **−4** |

结论：**故事感明显变强，BRAM 反而少 8%，LUT 只多几十个。** 在当前 WNS +0.023 ns 的处境下这是可接受量级；真正危险的是 24 格距映射与文字双口 ROM 流水，不是这些改动。

### 2.10 该明确拒绝的

建议写进计划当"拒绝清单"，比写十条"要做"更有用：

- 开场动画、立绘、对话选项、分支结局
- 有背景故事和名字的配角（一个会说型号的设备，比三个有简历的船员更可信）
- 说明性旁白、世界观文本、lore 收集
- 让语音承担状态播报
- 为"紧张"再加一条失败条件（O2 倒计时致死之类）——现有顶出失败已经够

### 2.11 落到现有轮次

| 轮次 | 加什么 |
| --- | --- |
| 2（布局／字库） | 颜色语法；幽灵改青色虚线；裂口先画成静态形状（阶段输入桩） |
| 3（核心／背景） | 裂口接阶段；核心亮度用 `charge_pulse` 做 2 bit 强度；删掉 2–3 处弥散变化 |
| 4（音频） | 全程底噪线；字幕停留；阶段音乐改"同一动机的变形" |
| 5（配音垂直验证） | 只验 7 句弧线，**重点验开局碎片句能不能听懂** |
| 6（集成） | 结尾 1.2 s 收束；失败时裂口反开；开局 1.5 s 静场 |

第 1 轮不用动。

### 2.12 如果只做三件

1. **核心当角色 + 语音清晰度随进度恢复**——省钱，且是唯一真正产生"人物"的改动。
2. **一处会愈合的伤口**——让玩家有东西可看、可比对、可记住。
3. **结尾那 1.2 秒**——决定这局是"打完了"还是"结束了"。

前两件几乎不加资源，第三件加不到 40 个 LUT。做完这三件，"故事感"就从"进度条机器"变成"一次有人在场的修复作业"。

# 第三部分 第二轮审阅（针对 2026-10-25 修订稿）

## 3.1 总体结论

**这次修订的质量高于我上一轮的建议。**

它没有顺着采纳，而是逐条回代码核对，改掉了我若干条错误（见 3.2）。这是审阅接口应有的健康状态：建议是输入，不是指令。

修订把上一轮点出的三个真实缺口——**时序、字库回收的条件依赖、预算不可证伪**——都补上了具体答案，并新增了一份门禁清单，把"什么算通过、不过怎么办"写成可验收的表格。这比原稿强一档。

剩下的主要问题已经不是"缺什么"，而是**同一个故事节拍被写了三遍**（见 3.4 A）。那不是文档瑕疵，是会变成"两块硬件做同一件事"的返工。

## 3.3 修订确实解决了的

1. **时序从"禁令"变成"方案"。** §11 点名真实最差路径 `hdmi_inst/VGA_1280_720_inst/vcounter_r_reg[5]` → `frame_inst/psel_r_reg[0]`（WNS +0.023）、最差 hold `acr_cycles_reg[12]` → `cts_reg[12]`（WHS +0.061），给出 P0→P3 四级候选流水与统一 `PIX_LATENCY`。先量再切，形状正确。并纠正了"音频也在同一条路径上"的混淆。
2. **BRAM 条件账变成公式加门禁。** `B_total = 8 + F + V`、净回收 ≥6.5、`B_without_voice + B_full_voice` 两段核算（G3 / G5）。正是所需。
3. **语音验证提前到 2C。** 把最弱资产从第 5 轮挪到字库门禁之后立刻验证；比"第 2 轮放静态兜底文本"更主动。
4. **成功演出改为"先静音、再回应、后结算"。** 优于原建议：原版背景音乐还在底下响，情绪是破的。
5. **失败不再撤销已修复部位**（§7.1、§11）。比"裂口反开"成熟：保住玩家成果，也保住因果。
6. **分数移出常驻 HUD 进结算；准备页两行目标卡替代强制等待；削减顺序成文。** 三条都对上原问题。
7. **`presentation` 不碰任务真源、`mission_hold` 单一真源、成功/失败音频拆分**——边界划得干净。

## 3.4 修订引入的新问题

### A（最高优先级）同一个"接口闭合"被写了三遍

| 位置 | 描述 |
| --- | --- |
| §3.1 核心状态列 | `REBUILD` "两组耦合接口闭合" → `RECHARGE` "主能量通道贯通，顶部等待最终锁定" |
| §6 核心绘制 | `RECONNECT` "上端连接器脱开" → `RECHARGE` "上端主接头进入充能" → 成功 "主接头闭合" |
| §7.1 背景主供能接口 | `RECONNECT` "明显开口、耦合片分离" → `REBUILD` "下半接合" → `RECHARGE` "耦合片闭合" → 成功 "接合状态保持" |

同一个动作、同一条时间线，三处各描述一遍。实现时几乎必然做出**两个同步动画的接口**——核心顶端一个、左上方一个。两处一旦不同步就是 bug，而且背叛了"一处可比较对象"的初衷。

**建议改法：**闭合事件只留一个实现。

- §6 的核心上端主接头 = 唯一的**开合**动画（位于玩家一直看的位置）。
- §7.1 的背景接口降级为**只表达供能流**：亮/暗、有无脉冲、方向，**不画开合**。
- §3.1 的"核心状态"列改为引用（"见 §6"），不再第三次描述。

这样"因"（背景的能流）与"果"（核心的接头）分工清楚，也省掉一整套几何。

### B 因果对象分居屏幕两侧

背景接口在 `x=[184,264), y=[112,160)`（左侧，NEXT 板正上方），核心在 `x=[1016,1064), y=[352,608)`（右侧）。"因"在左、"果"在右，中间隔着整个场地，玩家不会横穿 850 px 去配对。

按 A 改完后此问题自动消失——因为只剩一个对象。

### C G1 没有 +0.050 以下的退路

G1 要求下一轮 WNS/WHS 均 ≥+0.050，否则"先切短坐标→psel 路径、统一流水"。但没有规定：**切完之后仍是 +0.035 怎么办？**

门禁是二值的，而发布硬线是 ≥0。中间 0～+0.050 这段是规则空白，恰好是最可能落进去的区间（当前 +0.023，还需再赢 27 ps）。

**建议：给阶梯，不要开关。**

- **≥+0.050**：通过，允许叠加下一层装饰。
- **+0.030～+0.050**：允许继续，但门禁记录须写明"还有几级未切、每层独立 slack"，且下一轮只能做无新增组合深度的内容（字符／资产／音频）。
- **<+0.030**：停，回退布局，重新评估 24 格距。

另注：+0.050 ns 在 13.47 ns 周期中是 0.37%，属于习惯值而非物理阈值，当"趋势指标"比当"生死线"更合理。

### D 子预算加不到目标

| 项 | 值 |
| --- | ---: |
| 视觉轮上限（相对 R1） | 11,922 + 1,000 = **12,922** |
| G7 目标总量 | **13,615** |
| 剩余空间 | 13,615 − 12,922 = **693** |
| PCM + ADPCM 自估上限 | 300 + 450 = **750** |

**750 > 693。** 视觉轮用满额度时，音频组只剩 693 LUT，比自己估的上限少 57——目标会在无人违反任何单条预算的情况下被突破。

**改法（二选一）：** 视觉轮子预算降到 ≤950；或把目标改成 13,700，并明说 14,015 是唯一硬线、13,615 只是软愿望。

### E 阈值现在有三份副本

`≤120 LUT`（mapper）、`≤1,000`（视觉轮）、`≥6.5`（净回收）、`≤25/28`（BRAM）同时出现在计划书、门禁清单、评审取舍里。

调色板已经做到"单一描述源"，**自己的阈值没做到**。三份只要改一份，另外两份就成了假规格。

**改法：**数值只写在门禁清单，计划书正文改为引用（"见 G2"）。

### F 语音弧线被削弱了一格

原建议的机制是"**它说话越清楚，你修得越多**"。修订后 V0 成为 `YOU CAME.`，"轻微断续，但完整可懂，不删除关键音节"。

从可懂度看这是对的：8 kHz 4 bit 掐音节时，玩家可能听不出这是台词，而"开局数秒内建立前提"是 G4/G6 的硬要求。**这个退让可以接受。**

但弧线不必退回纯"语气变化"，可换成**不损失可懂度的可测梯度**：

| 维度 | V0 开局 | V1 | V6 成功 |
| --- | --- | --- | --- |
| 音节完整 | 全保留 | 全保留 | 全保留 |
| 底噪电平 | 最高（断续感靠噪声） | 中 | 无 |
| 句内断点数 | 2 | 1 | 0 |
| 词数 | 2 | 4 | 4 |

即：**用噪声底、断点数和词数做梯度，不碰音节。** 玩家听到的是"信号在变干净"，理解成本为零，也不多占 ROM——只是离线制备时多一档参数。

## 3.5 剩余建议

1. **先做 A。** 一个闭合事件、一个实现位置。这是本轮唯一会造成返工的结构问题。
2. **给 G1 加阶梯（见 C）**，填上 0～+0.050 的空白，否则 2A 结束时会出现无法裁决的裁决。
3. **对齐 D 的算术**：视觉 1,000 与音频 750，二者只能取一满额。
4. **G2 从"能辨"改成可测。** 现文为"15.6 英寸实屏能辨七类块、双方归属、NEXT/HOLD"，属主观判据。建议改为可复现：陌生操作者**在 400 ms 内正确命名方块类型** ≥90%；双人同屏下归属判断 ≥90%；并用一次灰度截图检查"仅靠颜色能否区分七类"（不能则须靠切角／角标补形）。这条比任何 LUT 预算更能决定 24 格距的生死。
5. **统一失败的语域。** 结算标题 `REPAIR FAILED`，AI 说 `NOT... YET.`——一个判决、一个邀请。二者挑一：标题改 `LINK LOST`，或台词改 `CORE OFFLINE.`。这是"故事感"里最便宜的一致性。
6. **定义停止点。** 还剩 2A／2B／2C／3／4／5／6 七轮，每轮都要全工程布线 + 14 套回归 + 337 项专项。第 1 轮是最小的一轮，已占满一个完整工作段；后续每轮工作量是其 3～5 倍。建议现在写死：**2A + 2B + 3 = V1（可玩、可读、四阶段可见，无语音）**；2C／4／5／6 = V1.1 氛围。这样项目在任何时刻被打断，都有交付得出去的版本。
7. **（可选，很便宜）让它对"打得漂亮"有一次反应。** 七句全是进度触发，等于一个定时器。唯一值得加的是**四行消行**：核心闪两档 + 两音动机，不说话。成本约 10～20 LUT，正好用掉 D 里那 57 LUT 的余量。

## 3.6 第二轮审阅的一句话总结

上一版的问题是"什么都写下来了，包括还没答案的部分"；这一版把**时序、字库回收、预算**三个缺口补上了答案，质量明显上了一档。

剩下最该改的已经不是"缺什么"，而是**同一个故事节拍被写了三遍**——那不是文档问题，是将来会变成两块硬件做同一件事的问题。
