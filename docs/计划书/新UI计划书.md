## 一、交付目标与一致性定义

完整版本以[新UI参考图冻结集](../参考图/最新参考图/新UI/README.md)为直接目标。最终上板画面在相同模式、数值、状态、动画相位及坐标下，以原生参考图对照；按下述用户追加的颜色规则映射后逐像素一致，不能以“布局差不多”“机械风相近”或预览能运行代替完成。

2026-10-28用户追加颜色规则：“取相近颜色，无相近颜色就再加颜色”。因此允许受控的近色合并，**不再要求未映射原RGB零差异，也不硬限制56色**。形状、比例、纹理位置、接口、文字底线与状态布局不变；原56个色号优先保持，找不到相近色就新增。每轮记录映射表、实际新增色数、误差指标及真实RTL图；原参考PNG不改。A1暂以CIELAB D65 ΔE76≤3试编，阈值是本轮可审核的工程选择，不是用户已经确认的永久视觉阈值。

必须保留参考图中的比例、轮廓、配色、文字样式与底线、分层材质、边框厚度、接口、遮挡关系。尤其不能重新设计管道、核心与刻度、船况头、NEXT、HOLD，不能用大色块或随意的几何框替代原材质。工程实现方式可以重构，输出画面按图验收。

资源不足的裁减版与完整版本分开管理：用户已允许按优先级裁减，裁减版应明确列出删掉的装饰区域和动态效果，保留区域仍对照原图。**裁减版不能标为“整图与完整参考一致”。** 优先尝试通过共享、无损存储和逻辑优化保住完整画面；确需删减时执行第六节，不能隐藏差异或修改参考图来消除差异。

真实游戏中的数值与状态读取正式逻辑。参考图中的15/35、02:18等是用于复现画面的输入样例，不允许硬编码进游戏。图片中的姿态与落点也不能代替真实方块、残骸、碰撞或提示计算。

## 四、资源目标与当前差距

资源基线来自[旧发布版资源报告](../reports/hold_ui_20261027_final/utilization.rpt)与[发布记录](../reports/hold_ui_20261027_final/release.json)，器件为`xc7a35tfgg484-2`。这些数值不代表第14轮新UI已经综合通过。

| 项目 | 旧发布版／器件 | 本计划口径 |
| --- | --- | --- |
| 整机Slice LUTs | 16,352／20,800 | 保留约800，按整机不超过20,000 LUT规划；不用满也是合格 |
| 相对旧发布版净增空间 | `20,000−16,352=3,648` | 含新增、替换回收及整合开销；不是UI每模块都能再加3,648 |
| LUT计数 | 15,140逻辑＋1,212存储＝16,352 | 用Slice LUTs总量，不能漏算LUTRAM／SRL |
| BRAM | 31／50个36Kb等效块 | 名义剩余19；仍受端口、位宽、布局及其他模块占用限制 |
| 寄存器／DSP | 6,630／41,600；16／90 | 按实际整机报告核对，不用它们换取LUT数字好看却造成其他资源溢出 |

800是最终保留余量，不是“UI只准用800 LUT”，也不是“旧版现在只剩800 LUT”。最终以对应源码、资产和参数的整机实现后报告确认；局部综合只能用于比较方案，不能给出最终通过结论。不能因整体还有LUT就保留超量BRAM或无法收敛时序的结构。

现有预览渲染器为五个`1280×720×24bit`整屏bank，合计110,592,000bit，单按容量就相当于3,000个36Kb BRAM；器件总共50个。`rom_style="block"`不保证异步读或多端口结构能按预期映射。因此第14轮是外观金样与仿真证据，**不能直接当作可上板架构**。

需一并处理的成本包括：整屏寻址、重复的新旧渲染层、文字可变除法／取余、组合颜色计算、模式bank重复材质以及RGB到正式显示链的转换。既有寄存级数、像素坐标、有效标记与输出延迟必须重新对齐，不能只在RGB末端加寄存器掩盖长路径。

## 五、实现路线：先保画面，再省实现成本

1. **冻结图与输入。** 本轮已冻结20张原生图及3张索引；实施时把相应夹具、动画相位和状态参数一起绑定。补齐缺失状态，先明确“要实现哪一张”。
2. **做无损可实现性评估。** 分解共同船壳、面板、飞船、管道、核心、字库与小型贴图，统计唯一图块、颜色、各行区段、透明区及可复用部分；比较共享图块、局部索引色、行程／区段编码、同步ROM与流水解码。先执行用户授权的近色编译，再保证编码／解码逐像素一致；不额外模糊、缩放或降纹理。
3. **建立单套公共渲染。** 四游玩模式、菜单、选关共用字库、块样式、背景与材质；模式只切换坐标和必要部件。逐步替换旧UI，待覆盖的入口接通后移除对应旧渲染路径，不把两套完整UI长期并联。不得误删仍服务暂停、结算或其他场景的旧分支。
4. **把高开销计算搬出逐像素路径。** 固定布局用常数坐标／分区，字符位置用预计算选择或计数器；段数、百分比、计时数字等在对应状态更新时计算并寄存。不能让大范围可变除法、取余、随机噪声或无界循环落在每像素组合路径。
5. **静态精细材质复用存储。** 沟道、法兰、锁链、倒角、铆钉与玻璃底面可烘焙为可复用小贴图，保证轮廓与颜色；动态只负责可见性、段数、局部效果与文字。无损烘焙属于优化，不计作“砍装饰”。
6. **同步审计输出链。** 检查新RGB如何进入HDMI与PC网口，调色板／位宽转换是否保留目标颜色，显示相位是否一致。不能因为24bit仿真图正确，就认为正式输出链已经同色；未经确认不假定板上有外部帧存，也不擅自改游戏数据或通信协议。
7. **整合测量后再裁减。** 分模块记录综合增量、删除回收量、整机总量、BRAM与关键路径；共享逻辑有重叠，不能机械相加局部估算。若完整画面与余量冲突，依第六节执行，不先凭感觉给模块许诺LUT数字。

无损存储与流水解码能否同时满足画面、带宽、BRAM和LUT，必须由第一个硬件原型给出证据。如果证明不可兼得，应列出具体成本与画面差距，再进入已授权的裁减顺序；不能事后把“图能仿真”解释为“完整目标已交付”。

## 六、UI优先级与不足时的裁减顺序

用户最新顺序优先：**先外围装饰UI，后动态效果**。先省静态装饰，不把消行、充能、状态切换等反馈提前砍掉。削减“装饰”不包括清除关键模块的外观身份。

| 等级 | 内容 | 资源不足时的处理 |
| --- | --- | --- |
| P0 必须保留 | 真实场地与方块／残骸、双NEXT／共享HOLD、必要数值、菜单选择、提示状态、核心／储备状态、对白与终局的必要信息 | 不删除，不显示假状态，不改游戏规则；文字可读与像素相位不能牺牲 |
| P1 重点保护 | 用户指定的管道与沟道／接口、核心壳体与六圈铁索、四阶刻度、船况头、NEXT／HOLD轮廓、P1/P2凸出肩部、统一字体与比例 | 以冻结图一致为目标；先共享／静态贴图优化。不能把这些关键细节当外围装饰一并删掉 |
| P2 动态反馈 | 消行火花、加成跳字、充能推进、状态扫光、呼吸脉冲、局部流光及过渡动画 | 装饰UI可裁项处理完仍不足时才削减；保留最低限度事件与状态提示 |
| P3 外围装饰UI | 星空、远景天体与漂浮残片、外围船壳的非功能装甲层、随机磨损、额外螺栓与通风槽、无功能走线 | 最先裁减；不侵入P0/P1区域，不改场地或挤动已定布局 |

## 八、验收方法与完成条件

1. **图像一致。** 同一夹具输入、数值、状态、动画相位及渲染延迟下，原生1280×720在已记录的颜色映射后逐像素比较，解码／合成目标为零差异；同时单列与原RGB的真实误差和合色变化，组件还原坐标比较。不能用缩略总览、相似度阈值、广泛遮罩或人工修图代替。不同状态没有参考时先补目标，不用一个静态帧证明所有动画正确。
2. **裁减透明。** 裁减版列出D/E项和精确变化区；区域外保持原参考一致。动态删减须列出取消／替代的状态，不把整块核心或整个游戏区遮掉。完整目标始终保留，不能反向覆盖金样。
3. **状态真实。** 关键边界包含LOCKED／HALF／ONLINE／成功8段、四阶切换、RESERVE预警、单人提示额度与有效期、HOLD预约／拒绝／到期、菜单选中、七条对白和终局覆盖关系。游戏核心计算保持原规格；只查画面不能替代最终相关功能验证。
4. **资源与时序。** 最终整机Slice LUTs≤20,000，预留至少800；全部资源适配器件并合法布通。完整布线后WNS≥0、WHS≥0、TNS=0、THS=0；不降低目标时钟，不用错误例外掩盖路径，不把800余量当作时序保证。
5. **上板呈现。** 用户检查HDMI及PC实际收流的颜色、边界、字形、底线、动态与可读性。FPGA构建通过与人工呈现验收分开记录，不能称已代用户上板验收。
6. **发布一致。** 最终源码、生成资产、模式参数、参考版本、裁减记录、验证结果和bit绑定同一输入指纹。候选留temporary；未满足正式发布条件不得替换`bit/Tetris.bit`。Git提交与GitHub推送仍分别按已有授权执行，不自动包含在写计划或出图之中。

最终交付应包含：可实现的公共UI源码与资产生成方式、当前选用参考版本、完整／裁减状态说明、最终整机资源账、真实RTL审核图及差异记录、相关验证与时序报告、对应bit和待用户上板核对项。只做到计划、预览、局部综合或大致相似，都不能标记为完成。
